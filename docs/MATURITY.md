# miko 成熟度路线

本文记录 miko 从“能自举并发布”走向“成熟跨平台高性能语言”时最影响质量的三个问题，以及每个问题的现状、边界和验收条件。

## 当前基线

截至 `v0.2.0-59`，miko 已具备以下工程能力：

- C++ 前端、LLVM 后端和自举后端能通过 44/44 difftest。
- 自举编译器两代输出固定点 `7D93916D417DC252`，每代通过 19/19 用例。
- 15/15 个典型静态错误提供 `file:line:col` 和插入符。
- Runtime 已有针对字符串的保守标记清扫 GC。
- LLVM 后端已经生成 DWARF，发布包可被 `llvm-dwarfdump` 识别。
- 发布矩阵覆盖 Linux x64/arm64、macOS x64/arm64、Windows x64/arm64。

这些结果证明了编译器闭环和发布闭环成立。下面三项决定它能否长期维护并承载真实项目。

## 1. 稳定的类型与错误模型

### 现状

类型兼容规则、推断规则和诊断文本分别存在于 C++ 前端、自举前端和 LLVM 生成路径中。当前检查已经覆盖未定义名称、调用参数、返回值、结构体字段、数组索引、枚举成员和不可调用值，但语言规范还没有成为单一来源。

错误处理也主要依赖退出码和文本诊断。运行时错误、编译期错误、外部资源错误和模块加载错误还没有统一模型。

### 目标

建立一份可执行的类型与错误规范，并让三个编译引擎遵循同一组规则。

### 实施顺序

1. 固化基础类型、默认整数宽度、隐式转换、可赋值规则和推断失败规则。
2. 固化数组、`vec<T>`、字符串、结构体、枚举、函数和模块的类型关系。
3. 为每条规则添加三引擎回归用例。
4. 统一诊断结构，至少包含错误类别、源范围、主消息和可选帮助文本。
5. 设计运行时错误值或错误返回约定，再扩展标准库 API。

### 验收条件

- 同一个源码输入在 C++、LLVM、自举三条路径上接受或拒绝一致。
- 每条类型规则都有正例和反例。
- 编译期错误都包含稳定的源范围。
- 运行时错误包含稳定错误类别和非零退出语义。
- 语言规范、测试用例和实现代码可以互相定位。

## 2. Runtime、并发与资源生命周期

### 现状

Runtime 已实现保守 GC，当前主要管理字符串对象。GC 通过栈扫描和寄存器 spill 保持兼容的 `ptr` ABI。堆对象之间没有引用关系，因此当前标记逻辑可以保持浅层。

Runtime 还没有正式的并发模型、线程 API、同步原语、任务取消方式、文件/socket 生命周期协议或外部资源析构约定。GC 的吞吐、停顿和多线程行为也没有稳定指标。

### 目标

在保留简单跨平台 ABI 的前提下，建立可测量的 runtime 资源模型。

### 实施顺序

1. 先定义 runtime 错误、资源句柄和关闭操作的语义。
2. 为文件、目录和进程句柄提供显式生命周期 API。
3. 增加线程、互斥锁、条件变量和一次性初始化的最小跨平台抽象。
4. 给 GC 增加线程注册、安全点、停顿统计和压力测试。
5. 对资源泄漏、双重关闭、并发关闭和异常路径建立回归测试。
6. 再决定是否引入 `defer`、RAII 风格作用域清理或所有权类型。

### 验收条件

- 文件和线程资源在正常、错误和提前返回路径都能关闭。
- 双重关闭和跨线程错误使用有明确结果。
- Linux、macOS、Windows 的同一 runtime 测试行为一致。
- GC 报告分配量、回收量、峰值和停顿时间。
- 压力测试在固定负载下不出现无界增长。
- 并发 API 的数据竞争和生命周期规则有文档和测试。

## 3. LLVM 与跨平台工具链稳定性

### 现状

LLVM 集成能自动探测若干本地路径，但平台版本仍不完全统一。Linux、Windows、macOS 的工作流使用不同的 LLVM 获取方式，macOS x64 仍依赖 brew 版本。LLVM 23 已经暴露过 API 和 IR 兼容问题。

Windows 发布坚持使用 llvm-mingw，不依赖 MSVC 作为发布链接器。CMake 的 Windows LLVM 开发构建仍需要与 LLVM 包兼容的 MSVC 生成器，这是构建 C++ 编译器的依赖，不改变发布包的 llvm-mingw 链接策略。

### 目标

让每个发布目标都使用可复现、可诊断、可验证的工具链组合。

### 实施顺序

1. 为每个平台记录 LLVM、clang、链接器、sysroot 和 runtime 版本。
2. 去除 macOS x64 对未固定 brew 版本的依赖。
3. 在配置阶段输出完整工具链摘要和支持范围。
4. 对不支持的 LLVM 版本提前失败并说明原因。
5. 建立目标平台与工具链版本矩阵，并让发布包携带构建元数据。
6. 对 C++ 开发构建与发布链接工具链分别验证，避免两者混淆。

### 当前版本门禁

| 目标 | 工具链约束 |
| --- | --- |
| Linux x64/arm64 | `llvm-18`，配置阶段要求 `llvm-config-18` 输出 `18.*` |
| macOS x64 | Homebrew LLVM，配置阶段要求 `22.1.8` |
| macOS arm64 | 官方 LLVM `22.1.8` 归档 |
| Windows x64/arm64 | llvm-mingw 发布归档标签 `20261117`，不使用 MSVC 发布链接器 |

### 验收条件

- 六个发布目标都使用明确版本的 LLVM/clang/链接器组合。
- 新机器上按文档执行可以复现构建，环境路径不会静默改变结果。
- 不支持的 LLVM 版本在 configure 阶段给出明确错误。
- 每个发布包都能报告目标架构、编译器版本和链接器版本。
- 发布 CI 的 difftest、bootstrap、static15 和 DWARF 检查全部通过。

## 当前进度

- 类型与错误模型：规范已建立，规则矩阵和统一错误结构仍待实现。
- Runtime：已加入 `MikoFile` 显式文件句柄 API，支持打开、读写、查询状态、关闭和销毁。关闭后的句柄保持可查询状态，重复关闭返回 0，便于错误路径清理。并发安全和语言层暴露仍待实现。
- LLVM 工具链：macOS x64 已增加 LLVM 22.1.8 版本门禁，避免 Homebrew 升级后静默使用不兼容版本。完整的六平台版本矩阵仍待统一。

## 当前执行顺序

第一阶段先完成三项基础设施：

1. 将类型规则整理为规范并增加规则矩阵测试。
2. 给 runtime 增加资源生命周期与并发抽象的最小接口，先覆盖文件句柄和线程安全统计。
3. 将 LLVM 工具链版本矩阵写入 CI，并先修复 macOS x64 的未固定版本依赖。

每一项都必须先有失败测试或失败门禁，再实现最小改动，最后运行完整发布门禁。
